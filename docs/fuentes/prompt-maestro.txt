### 3. Alcance funcional de la aplicación

El sistema representa una plataforma para gestionar solicitudes de crédito vehicular mediante un canal API único.

El flujo principal debe ser:

1. Un asesor inicia sesión.
2. Registra una solicitud de crédito vehicular con datos ficticios.
3. Proporciona los datos del cliente, vehículo y financiamiento.
4. Registra el consentimiento requerido.
5. Selecciona las financieras a las que quiere enviar la solicitud.
6. El backend valida y registra la información.
7. Se procesan los envíos a las financieras simuladas.
8. Cada financiera responde mediante su API mock.
9. La aplicación muestra las respuestas y estados.
10. El asesor compara ofertas y acepta una.
11. Se actualiza el estado final y queda evidencia de los eventos.

La interfaz web debe ser simple, agradable, responsive e intuitiva. Prioriza la claridad del flujo y una experiencia realista de uso, sin implementar funciones innecesarias.

Considera pantallas como inicio de sesión, dashboard, registro de solicitudes, listado y seguimiento, detalle, comparación de ofertas e historial.

Los roles de asesor, supervisor y administrador deben implementarse en la medida necesaria para demostrar autenticación, autorización y restricciones de acceso. Evita construir módulos administrativos extensos sin valor para la demostración.

Implementa prioritariamente las funcionalidades que permitan demostrar los RF más importantes, la arquitectura y la rúbrica. Genera una matriz que distinga requisitos completos, parciales, simulados, pendientes o fuera del MVP.

No simules funcionalidades afirmando que están implementadas cuando no lo están.

### 5. APIs simuladas de financieras

No disponemos de APIs bancarias reales ni necesitamos conectarnos a ellas.

Para el alcance del proyecto utiliza **dos financieras simuladas**:

- Banco Pichincha.
- Banco del Pacífico.

Son representaciones académicas ficticias. No afirmes que sus endpoints, protocolos, políticas o decisiones crediticias corresponden a sus sistemas reales.

Desarrolla un servicio mock independiente del backend principal, preferiblemente en Node.js.

Ese servicio debe poder ejecutarse y desplegarse por separado, con su propia URL de acceso, simulando que las financieras son sistemas externos.

Puedes ofrecer las dos financieras desde un mismo servidor mock con rutas o adaptadores independientes, siempre que mantengan contratos y comportamientos diferenciados.

Cada financiera debe poder producir respuestas variables, por ejemplo:

- Solicitud recibida.
- Solicitud en análisis.
- Crédito aprobado.
- Crédito aprobado con condiciones.
- Crédito rechazado.
- Solicitud de información adicional.
- Error temporal o timeout.
- Oferta con tasa, plazo, cuota, entrada y condiciones simuladas.

Define tasas, montos, plazos y respuestas razonables, pero ficticios.

Utiliza variabilidad controlada o generación pseudoaleatoria con semillas configurables para que las pruebas automatizadas sean reproducibles y las demostraciones puedan producir resultados predecibles.

Propón dos comportamientos de integración diferentes para demostrar el patrón Adapter. Por ejemplo, una financiera con JSON y webhook, y otra con un formato distinto y consulta de estado mediante polling.

La elección debe justificarse como una simulación académica, no como una descripción de las APIs reales.

Incorpora escenarios configurables para demostrar aprobaciones, rechazos, demoras, errores, reintentos y recuperación.

No uses credenciales bancarias reales ni datos personales reales.

### 6. Diseño arquitectónico

Evalúa REST, GraphQL y gRPC tal como exige la rúbrica. Documenta ventajas, desventajas y razones para seleccionar el estilo finalmente implementado.

Da preferencia a REST con OpenAPI para los consumidores, salvo que detectes una justificación técnica claramente superior.

Mantén un modelo canónico para las solicitudes de crédito y adaptadores independientes por financiera.

Analiza y aplica únicamente los patrones necesarios, entre ellos:

- Adapter / Anti-Corruption Layer.
- API Gateway, si se justifica y puede cubrirse con capacidades de la infraestructura seleccionada.
- Circuit Breaker.
- Reintentos y timeouts.
- Idempotencia.
- Procesamiento asíncrono.
- Paginación, filtros y ordenamiento.
- Autenticación y autorización.
- Rate limiting.
- Manejo normalizado de errores.
- Auditoría y trazabilidad.

Para cada patrón implementado explica qué problema resuelve, dónde se utiliza y cuál es su costo o limitación.

El procesamiento del envío no debe depender de esperar sincrónicamente la respuesta de las financieras.

Evalúa una solución duradera y sencilla de procesamiento asíncrono, por ejemplo un servicio administrado compatible con AWS o una alternativa persistente apropiada. No utilices tareas temporales en memoria como sustituto de una cola fiable.

Analiza también la consistencia de los datos, la concurrencia y la deduplicación de respuestas, teniendo en cuenta que MongoDB reemplaza a PostgreSQL.

Evita una arquitectura distribuida excesiva. Prefiere un backend modular con responsabilidades claras y componentes desplegables separados solo cuando exista una necesidad real.

### 13. Pruebas de rendimiento — k6

Utiliza preferiblemente k6.

Implementa y documenta los dos escenarios obligatorios:

**Escenario A — Carga sostenida**
- Aumento progresivo desde 0 hasta 100–200 VUs.
- Ramp-up de 2–3 minutos.
- Plateau de 5–10 minutos.
- Ramp-down de 1–2 minutos.

**Escenario B — Spike**
- Incremento abrupto hasta aproximadamente 500 VUs o entre 5 y 10 veces la carga normal definida.
- Pico de 1–2 minutos.
- Retorno inmediato a 0 y análisis de recuperación.

Las pruebas deben trabajar exclusivamente con datos ficticios y servicios simulados.

Genera reportes que incluyan:

- RPS y throughput.
- Latencia promedio.
- p90, p95 y p99.
- Tasa de errores y distribución de códigos HTTP.
- Consumo de CPU, memoria y recursos de base de datos, cuando puedan medirse.
- Comportamiento del rate limiting.
- Fallos y recuperación.
- Punto o intervalo de ruptura observado.

Para carga sostenida, utiliza la tasa de errores inferior al 1 % como objetivo de la rúbrica.

Conserva como objetivo funcional el p95 inferior a 2 segundos de los RNF y evalúa la meta ideal de 500 ms en endpoints síncronos estándar donde corresponda. Documenta cuál objetivo se aplica a cada operación.

No falsifiques resultados ni afirmes cumplimiento si las métricas no lo demuestran.

Si no se identifica un punto de ruptura exacto, indica el intervalo observado y la metodología utilizada, sin inventar un valor.

Controla el costo y seguridad del entorno de pruebas antes de ejecutar pruebas intensivas.

- Cuáles pasaron o fallaron.
- Qué está pendiente.
- Qué sigue.

No declares algo como completado sin evidencia.

Si surge un impedimento importante, explica el problema, presenta opciones sencillas y recomienda una.

Mantén un backlog actualizado y evita introducir trabajo adicional fuera del alcance académico.

**Prioridad final:** quiero una API funcional y bien diseñada, documentación comprensible, evidencia verificable de la rúbrica y una aplicación sencilla que pueda presentar con seguridad. Prefiero una solución pequeña pero completa antes que una arquitectura demasiado ambiciosa e incompleta.

Comienza analizando la documentación disponible y elaborando el diagnóstico inicial. Luego continúa con el proyecto siguiendo estas instrucciones.
