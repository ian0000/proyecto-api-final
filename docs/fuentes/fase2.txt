
Fase 2 — Arquitectura y patrones
Oct 9, 2026 · @alejandro
Para la Fábrica de Crédito elegimos REST con contrato OpenAPI para la comunicación con los consumidores y un núcleo orientado a eventos para la comunicación con las financieras. Todo se despliega como un monolito modular con dos roles, API y worker, detrás de un API Gateway. Con esta combinación se cumple el tiempo de respuesta que pide el caso, la caída de una financiera no afecta a las demás y se puede agregar una nueva financiera solo con un adaptador.

En resumen, usamos REST con contrato OpenAPI para todo lo que el asesor, el CRM y las financieras invocan, y mensajería asíncrona (una cola BullMQ sobre Redis) junto con webhooks para todo lo que depende de una financiera. gRPC no aporta en este caso, ya que no hay llamadas internas en cadena entre servicios que justifiquen su complejidad. GraphQL queda como opción futura para un BFF del comparativo, si el front móvil lo necesita.
3. Diagrama de arquitectura de software
La idea principal de la arquitectura es que la API nunca llame a una financiera mientras atiende una petición del asesor. La API deja el trabajo en una cola en Redis y responde de inmediato. Después, el worker toma ese trabajo y llama a cada financiera a través de su adaptador y su circuit breaker. Las respuestas regresan por webhook firmado (BG y BPAC) o por polling (Originarsa).

Arquitectura de software · vista de contenedores (C4 nivel 2)
El diagrama sigue las capas vistas en clase: la capa de presentación (front y CRM), la capa de aplicación (módulos de la API), la capa de integración (gateway, cola y adaptadores) y la capa de acceso a datos (PostgreSQL y Redis).

5. Flujo del envío asíncrono
En este flujo se ve por qué la arquitectura es asíncrona. El asesor recibe 202 Accepted en milisegundos aunque la financiera esté caída, ya que los reintentos, el circuit breaker y la dead-letter queue trabajan en segundo plano. De esta forma, el tiempo que el asesor espera no depende del tiempo que tardan los bancos.

Secuencia del envío asíncrono · 11 mensajes, 1 fallo reintentado
En el caso de Originarsa, el paso 9 se reemplaza por el polling que hace el worker cada cierto tiempo. Y si la misma respuesta llega dos veces, la deduplicación por X-Event-Id evita que se aplique de nuevo.
