
Fase 1 — Visión del producto y modelo de negocio de la API
Oct 9, 2026 · @alejandro
La Fábrica de Crédito es una plataforma API-First que funciona como canal único para las solicitudes de crédito vehicular de Corporación Maresa. Hoy cada solicitud se digita y se sigue por separado en el portal de cada financiera. Con la plataforma, el asesor registra la solicitud una sola vez y el sistema se encarga de enviarla a Banco Guayaquil, Originarsa y Banco Pichincha (BPAC), consolidar sus respuestas y comparar las ofertas.
1. Necesidad de negocio
El problema de Maresa no está en vender el vehículo, sino en todo lo que pasa después con el crédito. Cada solicitud se digita, se sigue y se compara por separado en tres financieras que tienen portales, formatos y tiempos distintos. Esto hace que el asesor pierda tiempo y que el cliente espere sin saber el estado, y en algunos casos la venta se pierde. Desde esta perspectiva, la necesidad de negocio es cerrar más créditos y más rápido con el mismo equipo de asesores.

2. Visión del producto
La visión del producto es que los asesores y supervisores de Maresa puedan obtener y comparar ofertas de varias financieras con un solo registro. A diferencia de los portales de cada banco, la plataforma centraliza el seguimiento, protege los datos del cliente y hace que Maresa sea dueña de la relación con el cliente y de los datos de cada operación.

El alcance incluye el registro, envío, seguimiento, comparativo, aceptación y desistimiento de las solicitudes. No incluye el desembolso ni la evaluación crediticia. Para el proyecto académico, las APIs de las financieras se simulan con un servicio mock que respeta el formato distinto de cada una.

5. Modelo de monetización
La API genera valor de tres formas, que se pueden activar por etapas. Primero, el ahorro de tiempo y el aumento de ventas, que es una monetización indirecta. Después, una comisión por cada crédito formalizado que pagan las financieras. Y finalmente, cuando la plataforma se abra, una suscripción por niveles para concesionarios externos.

Por ejemplo, con 1.000 solicitudes al mes, un 40 % formalizadas y un monto financiado promedio de USD 25.000, una comisión de 1 % generaría 400 × 25.000 × 1 % = USD 100.000 al mes. Estos valores son supuestos de trabajo y no datos de Maresa; el cálculo se puede actualizar con los datos reales que entrega el endpoint de indicadores.
Este modelo se apoya en el diseño de la API. La comisión solo se cobra cuando ocurre el evento FORMALIZADA, que queda registrado en una bitácora que no se puede modificar, así que la misma trazabilidad sirve como respaldo para la facturación. Además, las cuotas de cada plan se controlan en el API Gateway con el mismo rate limiting por consumidor que ya protege la plataforma.

1. Endpoints (URLs)
Base versionada /v1, recursos en plural, subrecursos para el ciclo de vida
/v1/solicitudes/{id}/ofertas
2. Métodos
GET consulta, POST crea o dispara una acción, PATCH modifica parcialmente
POST /v1/solicitudes/{id}/envios
3. Recursos
Solicitud, Respuesta por financiera, Oferta, Documento, Evento, Financiera
La solicitud agrega cliente, cónyuge/garante, vehículo y crédito
4. Parámetros
Path (id), query (page, size, estado, sort), headers (Idempotency-Key, If-Match, X-Correlation-ID), body JSON
GET /v1/solicitudes?estado=ENVIADA&sort=-creadoEn
5. Formato de datos
JSON, fechas ISO 8601 en UTC, montos en USD con 2 decimales; XML solo hacia el adaptador de BPAC
"monto": 26392.00
6. Códigos de estado
200, 201, 202 (envío asíncrono), 304, 400, 401, 403, 404, 409, 412, 413, 415, 422, 429, 503
Errores en RFC 7807 application/problem+json
7. Autenticación / autorización
OAuth 2.0 con JWT RS256: client_credentials para sistemas y token de usuario para el front; alcances (scopes) y roles; HMAC en webhooks
Authorization: Bearer <JWT>
8. Documentación
OpenAPI 3.0.3 contract-first, Swagger UI en /docs, ejemplos por operación
GET /openapi.yaml
7. Naturaleza de la API y dimensiones de diseño
Por su naturaleza, la Fábrica de Crédito es una API REST síncrona hacia los usuarios y orientada a eventos hacia las financieras. Es decir, al asesor le responde en milisegundos, mientras que el envío a los bancos se procesa en segundo plano y las respuestas llegan por webhook o por consulta periódica.
Las cuatro dimensiones del contrato digital
Dimensión
Cómo se manifiesta
Intermediaria
Se ubica entre el front de los asesores, el CRM/ERP y tres financieras heterogéneas; ninguno conoce los detalles del otro
Abstracta
El asesor ve un único modelo canónico; JSON en inglés (BG), snake_case con polling (Originarsa) y XML (BPAC) quedan ocultos tras los adaptadores
Contractual
El contrato OpenAPI se escribe primero y se verifica en cada build: las pruebas validan cada respuesta real contra él
Evolutiva
Versionado por URI (/v1); agregar una financiera solo requiere un adaptador y su configuración, sin cambiar el contrato público

Como supuestos, se toma BPAC como el crédito automotriz de Banco Pichincha y el crédito es vehicular. Las cifras de SLA, cobertura y precios son referenciales, y las APIs de las financieras se simulan con mocks basados en sus formatos.
